# api-contract

frontend와 backend를 서로 다른 사람이 담당하면, 둘 사이의 유일한 접점은 API의 요청/응답 형태다. 이 형태가 코드 안에만 흩어져 있으면 상대방 코드를 읽어야 알 수 있고, 그러다 어긋난다. `docs/api-contract.md`를 두 사람이 함께 보는 단일 출처로 유지한다.

## 문서 위치와 형식

`docs/api-contract.md`에 엔드포인트별로 아래 형식을 반복한다. 파일이 없으면 새로 만든다.

```markdown
## POST /api/example

### Request
```json
{ "field": "type — 설명" }
```

### Response
```json
{ "field": "type — 설명" }
```

### 비고
(에러 케이스, 상태 코드, 변경 이력 등 필요할 때만)
```

## PHASE_PLAN.md와의 관계

`PHASE_PLAN.md`에는 단계별로 "예정 API" 목록이 있다. 이건 계획 단계의 참고용일 뿐, 실제 계약이 아니다. 엔드포인트를 실제로 구현할 때 비로소 `docs/api-contract.md`에 확정된 형태로 기록한다. 예정 목록과 실제 구현이 달라졌다면(필드가 늘거나 줄었다면) `docs/api-contract.md`가 항상 우선한다.

## 갱신 규칙

- **엔드포인트를 추가/변경하는 쪽이 그 자리에서 문서도 갱신한다.** 구현하고 나중에 몰아서 정리하지 않는다 — 몰아서 정리하면 누락되기 쉽다.
- 기존 계약을 깨는 변경(필드 삭제, 타입 변경, 필수 여부 변경)은 "비고"에 변경 사유와 날짜를 남긴다. 상대방이 왜 바뀌었는지 코드만 보고는 알 수 없기 때문이다.
- 계약 문서와 실제 구현이 다르면, 구현을 문서에 맞추거나 문서를 구현에 맞추되 — 침묵 속에 둘 중 하나만 조용히 고치지 않는다. 어느 쪽이든 고친 뒤에는 상대방이 알아볼 수 있게 커밋 메시지나 비고에 남긴다.

## 검증

계약과 실제 코드가 일치하는지 확인하려면 `integration-checker` 에이전트를 사용한다. 이 스킬은 계약을 "쓰는" 방법을, `integration-checker`는 계약이 "지켜지는지" 확인하는 역할을 담당한다.
