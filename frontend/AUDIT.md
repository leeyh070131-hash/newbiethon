# 프론트엔드 재검토 — 2026-09-12

## 판정

**프론트엔드 체험판은 검증할 수 있지만, PRD 전체 충족 또는 실서비스 배포 적합 판정은 아직 불가능합니다.** 서버 계약, 실제 인증 설정, 데이터 영구 저장 및 다중 사용자 통합 검증이 남아 있습니다.

이 문서는 로컬 작업 사본을 대상으로 합니다. GitHub main에 업로드했다는 의미가 아닙니다.

## 담당 범위와 저장소 기준

- 루트 `AGENTS.md`, `frontend/AGENTS.md`, `PRD.md`, `PHASE_PLAN.md`, `docs/api-contract.md`를 대조했습니다.
- 앱과 수정·테스트·문서는 `frontend/`에만 있습니다. `backend/`는 변경하지 않았습니다.
- Next.js App Router와 Firebase 클라이언트 SDK를 사용했습니다. 단일 앱은 `frontend/app`에 있습니다.
- 실제 API 계약이 비어 있어 임의의 API 호출이나 서버 모델을 확정하지 않았습니다. `lib/demo.ts`의 계산은 화면 체험을 위한 것이며 서버 권한·동시성 검증을 대신하지 않습니다.
- `frontend/AGENTS.md`의 Next.js 안내 블록은 `next dev`가 자동 추가했습니다. 기존 담당/계약 규칙은 그대로 유지했습니다.
- 루트 단계 문서의 통합 완료 상태는 올리지 않았습니다. 프론트 구현 진행과 전체 단계 완료를 구분해야 합니다.
- Vercel 설정은 실제 적용하지 않았습니다. 향후 `frontend`를 Root Directory로 쓸 때 루트 `backend/` 코드를 단일 앱의 API 라우트에 연결하는 방법을 백엔드 담당자와 정해야 합니다.

## 이번 재검토에서 수정한 사항

1. 기존 휴대폰 테스트는 Chromium 화면 에뮬레이션만 사용했습니다. Firefox·WebKit 및 WebKit iPhone 화면을 검사 대상에 추가하고 개발 서버 대신 배포용 빌드를 검사합니다.
2. Node.js 안내가 테스트 도구 요구 버전보다 낮았습니다. `package.json`에 22.12 이상을 명시하고 안내 및 잠금 파일을 맞췄습니다. 검증 환경은 24.21.0입니다.
3. Firebase SDK가 첫 화면에서 즉시 로드되었습니다. 로그인 창이 필요할 때만 로드하도록 바꿨습니다. 실제 로그인 버튼 클릭 전 준비를 완료해 팝업 호출 앞에 추가 다운로드 대기를 두지 않습니다.
4. 팝업 Tab 이동이 Chromium/WebKit에서 브라우저 쪽으로 빠지는 동작을 발견해 처음/마지막 항목 순환을 명시했습니다. WebKit에서 팝업을 닫을 때 원래 버튼으로 선택이 복귀하지 않는 문제와 팝업 안 여백을 누르면 닫히던 동작도 수정했습니다.
5. 마이페이지 본문에 마일리지 잔액을 명시하고, 종료된 팟의 잘못된 ‘참여 중’ 표시를 ‘이용 이력’으로 수정했습니다.
6. 이미 위치를 허용한 경우 진입 시 가까운 출발지로 정렬하고, 해당 팟 상세를 보고 있을 때도 출발시간에 도달하면 연장 화면으로 전환하도록 보완했습니다.
7. 모바일 배너의 택시 그림이 잘리는 부분을 조정했습니다.

## 성능 측정

측정 대상: Windows / Node.js 24.21.0 / Next.js 16.3.5의 배포용 빌드, localhost Chromium, CPU·네트워크 제한 없음, 초기 방문 각 1회. `tests/e2e/performance.spec.ts`의 기록입니다.

| 초기 로딩 관측치 | 수정 전 | 수정 후 |
|---|---:|---:|
| JavaScript 압축 전 수신 본문 합계 | 609,303 bytes | 503,329 bytes |
| JavaScript 압축 후 수신 본문 합계 | 179,423 bytes | 148,918 bytes |
| LCP 관측치 — 큰 화면 요소가 표시된 시점 | 1,240 ms | 1,244 ms |
| CLS 관측치 — 예상치 못한 화면 이동량 | 0.00244 | 0.00244 |

초기 JavaScript 압축 후 수신량은 약 17% 감소했습니다. 관측된 표시 시간은 사실상 비슷하며, 이 자료로 실사용 속도가 개선되었다고 단정하지 않습니다.

성능 목표값·지원 단말 목록은 저장소에 별도로 정의되어 있지 않습니다. 실제 모바일 네트워크, 저사양 기기, 배포 지역, 많은 팟 데이터, 동시 접속, INP(입력에 대한 화면 반응 속도) 및 실사용자 통계는 측정하지 않았습니다. 서체는 외부 Google Fonts에 의존하며 실패하면 시스템 글꼴로 대체합니다.

## 호환성 범위와 남은 검사

최종 실행 결과:

- `npm test`: 규칙 단위 테스트 12개 통과.
- `npm run build`: 배포용 빌드 및 TypeScript 검사 통과.
- `npm run test:e2e`: 사용자 흐름 5개 × 브라우저/기기 설정 5개 = 25개 통과, 초기 로딩 측정 1개 완료. 합계 26개 통과, 실패 0개.
- 성능 측정을 Chromium에서만 실행하도록 지정하여 나머지 설정의 동일 측정 4개는 의도적으로 건너뛰었습니다. 사용자 흐름 검사를 건너뛴 것은 아닙니다.

- Next.js 설치 문서상 지원 범위는 Chrome/Edge/Firefox 111+, Safari 16.4+입니다. 이 앱을 그 모든 최소 버전에서 검사했다는 의미는 아닙니다.
- 자동 검사는 설치된 Playwright Chromium 153, Firefox 155, WebKit 26.6 및 모바일 화면 설정을 사용합니다. 실물 Android/iPhone, 실제 Safari·Edge 앱, 인앱 브라우저는 검증하지 않았습니다.
- 위치 거부 검사는 표준 거부 콜백을 재현하고, 위치 허용 검사는 브라우저 테스트 권한 및 가상 좌표를 사용합니다. 운영체제의 실제 권한 창과 GPS 정확도를 검증하지는 않습니다.
- 키보드 이동 검사를 했지만 스크린리더, 모든 색 대비·터치 영역을 포함한 접근성 전체 인증은 수행하지 않았습니다.
- Windows에서 빌드했으며 Linux/macOS 환경의 설치 및 Vercel 배포는 별도 확인이 필요합니다.

공식 참고: [Next.js 설치/지원 환경](https://nextjs.org/docs/app/getting-started/installation), [Playwright 브라우저](https://playwright.dev/docs/browsers), [Playwright 기기 에뮬레이션](https://playwright.dev/docs/emulation).
